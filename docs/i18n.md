# Internationalisation

This application is internationalised in four pieces, all of them in the tree
and gated.

| Piece                 | Gate                                                        |
| --------------------- | ----------------------------------------------------------- |
| Locale registry       | `src/i18n/locales.test.ts`                                  |
| Message catalogues    | `scripts/assert-i18n-catalogues.ts`                         |
| Direction-safe layout | `scripts/assert-logical-properties.ts`                      |
| `[locale]` routing    | `scripts/assert-locale-hrefs.ts`, and every route-list gate |

`en` is served at unprefixed paths and `ar` under `/ar`. The string extraction
is partial and the last section says exactly how far it goes.

## The locale registry

`src/i18n/locales.ts` is the single list of locales, and it deliberately
imports nothing. Both the server and the client need it, the build-time
catalogue gate needs it, and `<html lang>`/`<html dir>` need it — while
`next-intl/routing` pulls in a locale matcher and a header negotiator that have
no business in a client bundle that only wants to know which way the page reads.
`src/i18n/routing.ts` imports _this_, so there stays exactly one list and it is
the one with no dependencies.

`src/i18n/path.ts` is the other import-light module, and it exists because the
proxy's session gate has to answer "is this path protected?" before any of
`next-intl` has run. See **The session gate** below.

### Why `en` and `ar`

`en` is the default because every string in the repository is already written in
it. `ar` is the second locale, chosen over the usual `es`/`fr` placeholder for
the two reasons that make it carry its weight:

- **It reads right-to-left.** A second left-to-right locale exercises the
  message lookup and nothing else: every physical `ml-4` and `text-left` in the
  tree would still look correct in it. Only an RTL locale can show that the
  layout is direction-agnostic.
- **Its plural rules have all six CLDR categories** (`zero`, `one`, `two`,
  `few`, `many`, `other`) against English's two. That is what gives the
  catalogue gate something real to fail on — see below.

Adding a third locale is one line in `LOCALES` plus its direction in
`TEXT_DIRECTIONS` (the compiler fails until you add it) and a catalogue. The
gate then refuses to go green until that catalogue is complete.

## Message catalogues

`messages/<locale>.json`, nested freely, with ICU message syntax. `en` is the
reference: the gate compares every other catalogue against it in both
directions, so a key that exists only in `ar` is as much a failure as one
missing from it.

`scripts/assert-i18n-catalogues.ts` exists because a wrong translation is
invisible to every other check in this repository. A catalogue is a JSON file —
no types to violate, no imports to resolve, no code path to cover — so `tsc`,
ESLint, the unit suite and the build all pass over it without an opinion. The
three ways it goes wrong are these, and **none of them is a crash**:

1. **A missing key.** `next-intl` renders the key path itself, so a visitor sees
   `posts.recentTitle` where a heading should be.
2. **A flattened plural.** Someone translating from the English file writes
   `"count": "# منشورات"` instead of the ICU `plural` block. Every count renders
   the same form, and `#` is emitted literally because there is no plural
   argument to substitute into.
3. **A plural with the wrong categories** — the sharp one, and the whole reason
   `ar` is here. An `ar` catalogue carrying English's `{one, other}` is
   well-formed ICU, formats without error, and is grammatically wrong for 2, 3
   and 11, which all fall through to `other`. No type, no test and no render
   notices, because the output is a plausible string.

So the gate reads the required categories from `Intl.PluralRules` — CLDR as the
runtime has it, rather than a table here that could disagree with the one doing
the formatting — and then does two things per plural message: checks that every
required branch is declared, and _formats_ the message once per category through
`next-intl`'s own `createTranslator`, with a number CLDR assigns to that
category.

The one heuristic is how branch names are found. Parsing would need
`@formatjs/icu-messageformat-parser`, which is a transitive dependency rather
than a declared one; declaring it purely for a gate would add a direct
dependency on a package the application never calls. So the branch names are
read off the message source instead. That can over-report — prose reading
`...the other {count}` inside a plural message counts as a branch — which can
only make the gate _more_ permissive and can never fail a correct catalogue. The
format pass closes the gap from the other side regardless: a message the scan
misread still has to produce output for every one of its locale's categories.
`scripts/assert-i18n-catalogues.test.ts` pins both halves, including that
over-report.

`next-intl` is a **dependency** now. It was a devDependency for as long as the
catalogue gate was its only caller; the navigation wrappers, the request config
and the client provider are all in `src/`, so a production install carries it.

## Direction-safe layout

Logical CSS, everywhere. `ms-4` rather than `ml-4`, `border-e` rather than
`border-r`, `text-start` rather than `text-left`: these compile to
`margin-inline-start`, `border-inline-end` and `text-align: start`, which follow
the document's `dir` instead of pinning themselves to a side.

`dir` is set on `<html>` in `src/app/[locale]/layout.tsx`, from the registry, and that
attribute is what makes the rest of it work — with no `dir`, every logical
utility resolves left-to-right and the whole exercise guards a property nothing
reads.

`scripts/assert-logical-properties.ts` is the half that outlives the commit that
did the conversion. Converting the tree is an afternoon; keeping it converted is
the problem, because **`ml-4` and `ms-4` render identically in English** —
identical pixels, identical screenshots, identical axe output — and differ only
once the document is `dir="rtl"`. A new `mr-2` is a change that looks right,
tests right and reviews right, and puts a margin on the wrong side of the one
locale nobody on the team reads.

The gate scans the contents of string literals rather than grepping the file,
and both reasons are in this repository:

- `rounded-lg` contains `rounded-l`, and `border-e` would be a nonsense
  replacement for it. Matching whole whitespace-delimited tokens tells them
  apart.
- Prose names these utilities — this document is full of them, and so is
  `src/i18n/locales.ts`. Scanning only string literals skips every comment by
  construction, so documenting the rule cannot break the rule.

A value also has to _look_ like a Tailwind value. The first version matched
`^right-(.+)$`, which is also the shape of the phrase "right-to-left" — so a
test named `"reads right-to-left"` failed the build, advising `end-to-left`.

### What stays physical on purpose

`left-1/2` and `right-1/2` are centring idioms: paired with `-translate-x-1/2`
they are symmetric about the centre and behave identically in both directions.
Their logical spellings are the ones that break — `start-1/2` resolves to
`right: 50%` under RTL while `-translate-x-1/2` still pulls leftward, which
moves a centred dialog off-screen. `inset-x-*` is symmetric and needs no logical
form, and `translate-x-*` is not flipped by `dir` at all, so banning it would
imply an alternative that does not exist.

### What the gate cannot see

It checks class names, so it has nothing to say about **directional glyphs in
copy**. `app/blog/layout.tsx`, `app/photos/layout.tsx` and
`app/pricing/layout.tsx` each render a literal `← Home`, and that arrow points
the wrong way under RTL regardless of how the element is laid out. The fix is
not a utility: it is either a mirrored icon or the arrow moving into the
catalogue so each locale supplies its own, which makes it part of the string
extraction rather than of this pass. It is listed here so it is a known gap
rather than a surprise.

## `[locale]` routing

The route tree is `src/app/[locale]`, with `src/app/api` and
`src/app/global-error.tsx` left above it. `src/app` has no `layout.tsx` and
cannot have one: a root layout renders `<html lang>`, `lang` is the locale, and
the locale is that segment — so `src/app/[locale]/layout.tsx` _is_ the root
layout.

### `localePrefix: "as-needed"`

`en` is served unprefixed (`/dashboard`), `ar` under `/ar/dashboard`, and
`/en/dashboard` is redirected to the unprefixed form so each page has one
canonical URL.

The usual argument for `as-needed` is that the majority locale keeps the shorter
URL and every shared link still resolves. The argument that decided it here is
narrower: the canonical path of a routed experiment is load-bearing in three
places that are not in `src/app` at all. `next.config.ts` pins `Cache-Control`
on `/pricing`, `src/proxy.ts` rewrites it to `/pricing/v/<variant>`, and
`scripts/assert-experiment-wiring.ts` holds the registry against both. Under
`always`, every one of those becomes a set of paths and the `headers()` block —
which matches the incoming path, before any rewrite — has to enumerate them.
Under `as-needed` the existing entry keeps covering `en` and `/:locale/pricing`
is additive.

### Public paths and segment paths are different things

This is the distinction the rest of the routing rests on, and it did not exist
before the segment did:

|                  | Example       | Where it belongs                                |
| ---------------- | ------------- | ----------------------------------------------- |
| **Public path**  | `/pricing`    | an `href`, a `Location` header, the address bar |
| **Segment path** | `/en/pricing` | a rewrite target, a prerender-manifest key      |

`localisePath` and `internalPath` in `src/i18n/path.ts` are those two, and they
differ only for the default locale — which is why one helper would read as
sufficient and be wrong in opposite ways at each call site. A rewrite to the
public path 404s for `en`; a redirect to the segment path bounces through
`next-intl`'s canonical-URL redirect on the way back out.

### The proxy

Six concerns in a fixed order: the rate limit, locale negotiation, the session
gate, experiment routing, the Content Security Policy, the hardening headers.

`next-intl`'s middleware is used for its **redirects only**. Its rewrite is
rebuilt in `src/proxy.ts`, because that file already owns a rewrite — `/pricing`
becomes `/pricing/v/<arm>` for a bucketed visitor — and two middlewares cannot
each return the response. Letting `next-intl` return its own would lose either
the experiment arm or the CSP request header that carries the nonce into the
render.

The locale every later step works in is read back off the path rather than out
of `next-intl`'s response, and that is sound rather than a shortcut: under
`as-needed` a request whose locale differs from the one its path implies is
_redirected_, never passed through. So a pass-through at a prefixed path is that
prefix's locale and a pass-through at an unprefixed path is the default. There
is no third case, and reading `x-middleware-rewrite` back out of the response
would be depending on an internal header to learn something the path already
says.

`/api/*` is excluded from negotiation entirely. It is not under the segment, and
`next-intl` does not know that: the first segment of `/api/health` is not a
locale, so it reads the path as unprefixed and would rewrite it to
`/en/api/health` — or, for a visitor whose cookie says `ar`, _redirect_ to
`/ar/api/health`. Either is a handler that does not exist, and the second turns
every `fetch` from an Arabic page into a 404, `/api/auth/callback` included.

### The session gate

`PROTECTED_PREFIXES` and `ADMIN_PREFIXES` are public paths, so `/ar/dashboard`
starts with none of them. `authorized` in `src/auth.config.ts` strips the locale
with `splitLocalePath` before matching, and builds its refusals at the request's
locale so an anonymous visitor to `/ar/dashboard` lands on `/ar/login`.

Without the strip, the proxy stopped gating every route in every locale but the
default. This repository is built so that is a defence-in-depth regression
rather than an open door — every gated route also reads the session next to its
data, `/admin` included, which is why the role check sits inside
`<AdminSessionFields>` — but the refusal moves from _before the response_ to
_inside a streamed boundary_, and nothing in the suite looked at a prefixed
path. `src/app/[locale]/(dashboard)/auth-guards.test.ts` does now.

Two details in `splitLocalePath` are worth the lines they cost. The first
segment is compared **whole**, because `/arabic` begins with `ar` and is not an
`ar` path, and because `//evil.example` has an empty first segment that must not
be read as one. And `en` is stripped even though `/en/dashboard` is never
served, because the gate runs before `next-intl`'s redirect — a path the gate
declines to recognise is a path it declines to protect, which would make the
ordering of two middlewares a security property.

### Why the client provider is ours

`src/components/providers/intl-provider.tsx` is a three-line `"use client"`
wrapper, and it has to exist. `next-intl` exports two different things under the
name `NextIntlClientProvider`: imported from a Server Component it resolves to
an **async** component that fills in whichever of `locale`, `messages`,
`formats`, `now` and `timeZone` it was not given by awaiting the request config.
Under `cacheComponents` an async Server Component reading uncached data has to
sit inside a `<Suspense>`, and this one sits in the root layout above every
route — so the build ended on all 86 pages with
`Uncached data was accessed outside of <Suspense>`. Passing `locale` and
`messages` was not enough: the other three are each defaulted with their own
`await`.

Wrapping the providers in a `<Suspense>` would have made the error go away by
putting every page's body behind a boundary, which is the regression
`scripts/assert-route-shape.ts` and `scripts/assert-streaming-boundaries.ts`
exist to catch — a green build and two red gates. From a `"use client"` module
the same name resolves to the synchronous provider, which takes what it is
handed; nothing here is per-request, because the locale comes from
`generateStaticParams` and the catalogue is a static import.

For the same reason `src/i18n/catalogues.ts` holds the catalogues as static
imports rather than `await import(\`../../messages/${locale}.json\`)`. A template
literal in an `import()` makes the whole directory a dynamic dependency, and the
read is asynchronous — the one kind a prerender cannot contain.

`setRequestLocale` is called in the layout so the subtree stays prerenderable:
`useTranslations()` in a Server Component otherwise resolves the locale from the
segment at request time, and reading a dynamic segment's value is a request-time
read.

### Navigation

Everything in `src/app` and `src/components` imports `Link`, `usePathname`,
`useRouter` and `redirect` from `@/i18n/navigation`. A plain
`<Link href="/posts/1">` on an `ar` page points at the `en` document: the href
is an absolute path, it carries no locale, and `as-needed` resolves an
unprefixed path to the default locale. The same wrapper fixed `NavLinks`, whose
active-link comparison was against a pathname that would have had `/ar` on the
front and so matched nothing in any non-default locale — a navigation that stops
telling a screen reader which page it is on, in the one locale nobody on the
team reads.

`href` is `string` rather than Next's generated `Route`, and that is forced
rather than chosen. The filesystem is `src/app/[locale]/posts/[id]`, so
`next typegen` emits `/[locale]/posts/[id]` and considers `/posts/1` to be no
route at all — while `/posts/1` is the URL `en` is served at. The generated type
describes the segment tree and these wrappers take the public path; nothing can
be both. Declaring `pathnames` in `src/i18n/routing.ts` would restore a typed
`href` at the cost of a second hand-maintained inventory of every route in the
application.

`scripts/assert-locale-hrefs.ts` is the replacement, and it carries four rules:
every href literal resolves to a route on disk (R1), no href carries a locale
prefix of its own (R2), the files whose hrefs it cannot read are declared (R3),
and internal navigation goes through `Link` rather than a bare `<a>` (R4).

R4 is also a replacement, for `@next/next/no-html-link-for-pages`. That rule
asks whether an `<a href>` names a page and answers it by building the route set
from the app directory — and with a dynamic segment at the root, _every
single-segment path_ names one. It began reporting
`<a href="/elsewhere/">` in a skip-link test as a link to a page, 24 errors in
all, none of them one. R4 asks whether the href _resolves_ instead, and found
two raw `<a>` elements doing real internal navigation that the lint rule had
never reported: the register button in the pricing table, and the "Open full
page" link out of the `@modal` interceptor. The second has to stay an `<a>` —
a full page load is the point — so its href goes through `getPathname`.

### What the restructure cost the gates

Every gate carrying a route list needed the locale axis. The per-route
expectation stays written down and only the axis is derived, because shape is a
property of the route and not of the language it renders in — and a hand-written
product would mean every entry appearing once per locale, where the forgotten
one is a route nobody is checking in the locale nobody reads.

Three of those updates found something:

- **The shell needles were English literals**, so the six dashboard shells
  failed for `ar` on shells that were correct. They are catalogue keys now. That
  is sharper than the literal was rather than merely equivalent: `/ar/dashboard`
  reported `"Dashboard"` as _present_, matching the `/dashboard` href next to
  the Arabic label. A needle a URL can satisfy cannot tell a prerendered
  navigation from a prerendered link to one.
- **`srcRoute` points at the segment form** for both locales, so counting
  prebuilt pages by it counted them once for both. A locale whose
  `generateStaticParams` returned `[]` while the other's did not would have been
  invisible.
- **The bundle budget's shared baseline collapsed to zero.** `sharedChunks` is
  an intersection across every document, and the `[locale]` fallback shells
  reference almost no scripts — so the gate reported
  `Shared by every route: 0.0 kB across 0 chunk(s)` against a 155 kB budget,
  which passes trivially, and "own" cost became first load for every route in
  the table. Those shells are excluded now.

Two things genuinely regressed and were fixed rather than exempted:

- **`/_not-found` lost its landmark.** `not-found.tsx` is inside the segment
  now, where it covers an unmatched _single_ segment — `/nope` is read as a
  locale, fails the layout's `isLocale` check, and renders that boundary. It
  does not cover `/a/b/c`, which matches nothing and gets the document Next
  writes above the whole layout hierarchy: its own built-in 404, with no
  `<main>` and no skip link. `src/app/global-not-found.tsx` is the fix, which is
  why `experimental.globalNotFound` is on.
- **Every route gained 6.0 to 14.8 kB gzipped**, all of it the `use-intl`
  runtime that the provider and `useTranslations` put in the client graph. The
  budgets were raised with that measurement recorded in `ROUTE_BUDGETS`. Two
  checks establish that the locale itself is not a factor: `/en/upload` and
  `/ar/upload` reference the same twenty chunks with none unique to either, and
  the same 584 bytes of inline script. The catalogues go into the RSC payload
  rather than into a chunk.

The `[locale]` fallback shells are exempted in three gates — focus management,
font loading and the bundle budget — and they are genuinely empty. The root
layout narrows the segment and calls `notFound()` above everything it renders,
so for an unknown param there is nothing it _can_ prerender. That is the right
trade: a layout that wrote the chrome before deciding whether the locale existed
would serve `/xx/dashboard` as a complete, plausible, 200-answering page, and
because `next-intl`'s request config falls back to the default locale, every
string in it would be correct.

## What is extracted, and what is not

The catalogues are rendered by the navigation, the theme control, the skip link
and the recent-posts panel. That last one is where both plural messages
actually format — `posts.count` and `posts.draftCount` were checked by
`scripts/assert-i18n-catalogues.ts` and displayed by nothing, which is a gate
guarding a message no visitor could see. It is also the one place the six Arabic
CLDR categories are visible: `0` takes the `=0` branch, `1` the `one` branch,
`2` the `two` branch, `3`–`10` the `few` branch and `11`–`99` the `many` branch,
against English's two forms.

Everything else is still an English literal in a component: the page headings,
the dashboard stat tiles, the form labels and validation copy, the editor and
upload controls, the error and empty states. Those are extraction work, not
routing work — each one is a key added to two catalogues and a literal replaced,
and the gates above do not change when one moves. `scripts/assert-i18n-catalogues.ts`
will not let a key exist in one catalogue and not the other, and the
`AppConfig` augmentation in `src/i18n/messages.d.ts` will not let a typo
compile; what neither can tell you is that a string was never extracted at all.

The known gap the direction-safe pass left is still open and still worth
repeating here: `app/[locale]/blog/layout.tsx`, `app/[locale]/photos/layout.tsx`
and `app/[locale]/pricing/layout.tsx` each render a literal `← Home`, and that
arrow points the wrong way under RTL however the element is laid out. The fix is
a mirrored icon or the arrow moving into the catalogue, which makes it part of
the extraction above rather than of the routing.
